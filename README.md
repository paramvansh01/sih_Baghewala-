# Baghewala Well-to-Surface Digital Twin (CSS + SRP)

A physics-based digital twin of a cyclic-steam-stimulated (CSS) heavy-oil well produced by a
sucker-rod pump (SRP), plus machine-learning models trained **from scratch** on the twin's
output, and optimisers whose recommendations are **verified back in the physics twin**.

> **Status of the data: synthetic.** Baghewala well-level data (production, CSS cycles, VFD/SRP
> logs, failures) are not public. Every training table here is generated by the physics twin
> from parameters listed with their provenance in `config/field.yaml`. The pipeline is built so
> OIL's real tables can replace the synthetic ones (see "Using real field data").
> Results and all numbers: `artifacts/report.md` (regenerated by the pipeline, nothing typed by hand).

## Quick start

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
PYTHONPATH=. .venv/bin/python -m twin.cli all      # generate -> train -> optimise -> report (~3 min)
.venv/bin/python -m pytest                          # verification suite
PYTHONPATH=. .venv/bin/python -m twin.cli params   # every parameter with status + source
```

Individual stages: `python -m twin.cli generate | train | optimise | report`.
**Live dashboard (real-time monitoring, prediction, optimisation):**
`PYTHONPATH=. .venv/bin/python -m twin.cli live` → http://127.0.0.1:8790/ (batch report at `/report/`).

The live view runs every well's physics twin one day per tick as a **simulated field feed**
(clearly labelled; replace with a SCADA/historian adapter for field use). Two fleets start from the
identical end-of-history state: *current practice* (manual SPM rules, historical CSS settings) and
*digital-twin control* (twin SPM/speed controller + surrogate-optimised CSS settings that are
verified in the physics twin before being applied). For the selected well it shows measured vs
ML-forecast rate and temperature for the current cycle, applied vs recommended SPM/speed ratio,
the rod-load envelope and Goodman loading, and a dynamometer card simulated at today's operating
point with the CNN diagnosis next to the label the physics implies. Pump faults can be injected
into the card simulation to exercise the diagnosis. Live CNN-vs-physics agreement is measured by
`python -m twin.cli livecheck` and reported in the batch report.

## What maps to the problem statement

| Requirement | Where | How |
|---|---|---|
| Integrate reservoir, wellbore, surface | `twin/physics/reservoir.py` | Daily coupled loop: heated zone → inflow → tubing temperature/viscosity → SRP capacity, loads, energy → production |
| Optimise CSS cycle parameters | `twin/optimize/css_optimizer.py` | Surrogate search over steam volume, injection pressure, quality, soak, cut-off, min production days, initial SPM; top candidates re-simulated in the physics twin |
| Predict reservoir heating/cooling & production | `twin/models/trajectory.py`, `twin/models/css_surrogate.py` | Daily oil rate + bottom-hole temperature by production day; cycle oil, water, length, energy |
| Continuously optimise SPM / stroke speed | `CSSWellSimulator.choose_twin` | Daily choice of SPM and downstroke/upstroke speed ratio (VFD / hydraulic unit) avoiding floating and Goodman overload, targeting fillage, minimising power |
| Detect rod floating, minimise impact loading | `twin/models/card_cnn.py`, `srp_analytic.py`, `rodpump_fd.py` | CNN diagnoses cards (7 classes incl. floating, unseated pump); floating is *predicted* before it happens from viscosity + speed and avoided by the controller; lift-limited cut-off ends a cycle instead of pumping into rod damage |
| Pump efficiency, reliability | same | fillage, Goodman loading, impact strokes tracked per day |
| Steam & energy cost | `css_optimizer.py` | fuel from steam tables (IAPWS-IF97), SRP electrical energy, net value per cycle-day |

## Architecture

```
config/field.yaml ──► twin/physics/ ─────────────────────────► synthetic history & cards
  (value, unit,        fluids.py     ASTM D341 viscosity, API density     twin/data/
   status, source)     steam.py      IAPWS-IF97 (iapws package)
                       thermal.py    Marx–Langenheim heated area,
                                     conduction losses/zone growth
                       wellbore.py   Ramey (1962) heat loss & production T profile
                       reservoir.py  CSS cycle simulator + SRP controllers
                       srp_analytic.py  fast loads/floating/Goodman/energy
                       rodpump_fd.py    finite-difference rod string + pump chamber (cards)
                                                   │
                                                   ▼
twin/models/  css_surrogate.py (GBM/ridge/ensemble, grouped CV)  trajectory.py (GBM)
              card_cnn.py (1-D CNN, PyTorch, random init)
                                                   │
                                                   ▼
twin/optimize/ css_optimizer.py (surrogate search → physics verification)
               srp_eval.py (manual vs twin controller, FD spot checks)
                                                   │
                                                   ▼
                              artifacts/report.md + figures + metrics JSON
```

## How "nothing hardcoded" is enforced

* Every physical/field number lives in `config/field.yaml` with `status`
  (`published` / `problem_statement` / `assumption` / `physical_constant`) and a `source`.
  The loader rejects a parameter without a source, an unknown unit, or a non-numeric value.
* Numerical/ML settings (grid sizes, epochs, seeds, scenario ranges for cards) live in
  `config/pipeline.yaml`.
* Optimiser bounds come from the training data envelope (stored with the model), not from code.
* The report reads every number from `artifacts/`.

## How "trained from scratch" is verified

* CSS surrogate and trajectory models: scikit-learn estimators fitted on the generated tables;
  test wells are disjoint from training wells (`tests/test_models.py`).
* Card CNN: randomly initialised PyTorch network; the report shows the initial validation loss
  equals chance level ln(7) and the loss curve down to the final value; a test asserts this.
* Baselines are always reported next to the models (mean, "repeat previous cycle", ridge,
  logistic regression, physics rule), so an ML score is never shown without context.

## Physics verification (tests/)

* IAPWS saturation values vs steam tables; Walther curve passes exactly through the published
  viscosity point.
* Marx–Langenheim closed form vs an independent step-by-step numerical heat balance (<1 %).
* Ramey production-temperature profile vs ODE integration; wellbore heat-loss integral vs quadrature.
* SRP kinematics vs numerical averaging; static loads vs statics; Goodman definition.
* Reservoir simulator conserves energy, injected water and oil to 1e-9 over multiple cycles;
  rate never exceeds pump capacity or reservoir potential; pressure solver reproduces the
  steady-state series-resistance formula.
* FD rod model: quasi-static loads vs analytic; unseated pump carries no fluid load; slower
  downstroke reduces floating; analytic floating check agrees with the FD model (≥85 % required).

## Sanity checks against published figures (reported, not fitted)

The report compares the synthetic field with OIL's published ~1,100–1,202 bopd and the CSS
pilot's "five to six fold" production increase. **The synthetic field produces far less than
the real field**, i.e. the assumed (unpublished) reservoir and tubing-flow parameters are
pessimistic. Absolute production numbers from the synthetic study are not Baghewala
forecasts; model-vs-baseline and policy-vs-policy comparisons are what it supports.

## Using real field data

Replace the files in `artifacts/data/` with tables in the same schema, then run
`python -m twin.cli train` (surrogate, trajectory model and card CNN train directly on them).
The physics-verification step (`optimise`) re-simulates each well in the twin; for real wells
that needs a per-well calibrated twin, which is **not implemented yet** — the optimiser stops
with an error rather than verifying real wells against synthetic ones. Expected schema:

* `wells.csv` — one row per well: `well_id, k (m2), h, phi, s_oi, r_e, p_i (Pa), t_r, api,
  mu_ref (Pa.s at 50 C), walther_b, stroke, pump_depth, cold_oil_m3d`.
* `cycles.csv` — one row per CSS cycle: controls (`steam_t, inj_pressure_MPa, quality_surface,
  soak_days, cutoff_m3d, min_prod_days, spm_init`), history (`cycle_no, cum_oil, cum_water,
  cum_steam_t, prev_*`) and outcomes (`oil_m3, water_m3, prod_days, energy_kwh, sor, ...`).
* `daily.csv.gz` — daily production records (`well_id, cycle_no, phase, prod_day, oil_m3d,
  water_m3d, t_bottom, spm, ...`).
* Dynamometer cards: `cards_meta.csv` + `cards_x.npy` (N × 2 × 128: position/stroke,
  load/rod weight in air) with labels from the failure/pump-unseating records.

Before trusting the physics twin for verification on real wells, calibrate (in this order) the
assumptions with the largest influence: permeability & net pay, Walther slope (lab viscosity vs
temperature), VIT overall U (wellhead temperatures), emulsion inversion water cut (rod loads),
pressure-dissipation and condensate-dispersal times (shut-in pressure, water recovery), and
the SRP geometry (pump size, rod string, stroke) of each well.

## Main limitations

* Single-layer, radially symmetric reservoir; lumped heated zone; two-region tank pressure;
  Dupuit gravity drainage; no steam flashing / solution-gas drive, geomechanics or interference.
* Tubing flow switches between oil- and water-continuous at an assumed inversion water cut;
  emulsion viscosity increase is ignored; rod drag uses annular Couette flow.
* Card model: single-taper rods, harmonic polished-rod motion, anchored tubing, ideal valves
  plus laminar leaks. Synthetic cards are cleaner than field cards.
* SRP results are dominated by the assumed emulsion inversion water cut and VIT U value (below
  inversion the tubing carries cold oil of 10^4–10^5 cP near surface). Measure both first.
* No rod-failure/workover cost model: the lift-limited cut-off (rod protection vs lost oil) is
  reported as a separate twin variant rather than priced.
* Economics use placeholder prices.
